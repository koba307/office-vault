# ТЕХНИЧЕСКОЕ ЗАДАНИЕ

## OFFICE VAULT — Корпоративная система хранения информации и управления офисными данными

**Версия:** 2.0  
**Статус:** Основная техническая спецификация проекта  
**Тип проекта:** Telegram-бот + серверная инфраструктура  
**Пользовательский интерфейс:** Исключительно Telegram  
**Язык интерфейса:** Русский  
**Основная платформа:** Linux VPS  
**Количество пользователей:** 10–50 сотрудников  
**Основное назначение:** Централизованное защищённое хранение, структурирование, поиск и предоставление сотрудникам рабочей информации, учётных данных, настроек, документов, файлов и медиа.

---

## 1. ОСНОВНАЯ КОНЦЕПЦИЯ ПРОЕКТА

Разработать полноценную корпоративную систему OFFICE VAULT для централизованного хранения и управления рабочей информацией организации.

Система должна работать исключительно через Telegram-бота.

Не разрабатывать веб-панель, личный кабинет, браузерный интерфейс, отдельный frontend или пользовательский сайт.

Все пользовательские и административные функции должны быть доступны через Telegram:

- Просмотр информации.
- Добавление записей.
- Редактирование.
- Управление категориями.
- Загрузка файлов.
- Скачивание файлов.
- Поиск.
- Импорт.
- Экспорт.
- Управление доступом.
- Управление сотрудниками.
- Аудит.
- Избранное.
- Архив.
- Резервное копирование.
- Администрирование.

Серверная инфраструктура должна работать независимо от Telegram и обеспечивать надёжное хранение всех данных.

Главная задача — создать единое корпоративное хранилище, из которого сотрудники смогут самостоятельно получать необходимую им рабочую информацию без постоянного обращения к руководителям.

### 1.1. Основной принцип организации информации

Главное меню должно быть разделено на четыре основные категории сотрудников:

1. Холодка
2. 2й Этап
3. Клоузеры
4. Общее

Это четыре основных раздела пользовательской навигации.

Внутри каждого раздела размещаются типы информации:

- Логины и пароли.
- SIP и телефония.
- Ссылки.
- Настройки.
- Инструкции.
- Файлы и документы.
- Фото, видео и аудио.
- Прочая информация.

Принципиально важно: тип информации и категория сотрудников — разные сущности.

Например:

В разделе «Холодка» могут находиться собственные логины, SIP-данные, инструкции, ссылки и документы.

В разделе «Клоузеры» могут находиться другие логины, SIP-аккаунты, ссылки и инструкции.

Раздел «Общее» содержит информацию, предназначенную для всех сотрудников, которым разрешён доступ к этому разделу.

Нельзя объединять четыре категории сотрудников в одну общую категорию данных.

### 1.2. Цели проекта

- Единое централизованное хранилище.
- Разделение информации по направлениям работы сотрудников.
- Контроль доступа к данным.
- Хранение логинов и паролей.
- Хранение SIP-аккаунтов.
- Хранение ссылок и настроек.
- Хранение инструкций.
- Хранение документов и медиа.
- Быстрый поиск.
- Возможность добавления произвольной информации.
- Управление содержимым через Telegram.
- Контроль действий пользователей.
- Импорт и экспорт.
- Резервное копирование.
- Возможность расширения системы.

## 2. АРХИТЕКТУРА И ТЕХНОЛОГИЧЕСКИЙ СТЕК

Использовать серверную архитектуру с централизованной базой данных.

Архитектура должна быть модульной, но без избыточного разделения на микросервисы.

Для проекта на 10–50 сотрудников оптимально использовать модульный Backend с отдельными инфраструктурными компонентами.

### 2.1. Технологический стек

| Компонент | Технология |
|---|---|
| Язык программирования | Python 3.12+ |
| Telegram Bot | aiogram 3.x |
| Backend | FastAPI или внутренний сервисный слой |
| База данных | PostgreSQL |
| ORM | SQLAlchemy 2.x |
| Миграции | Alembic |
| Файловое хранилище | MinIO / S3 |
| Кеш и временные состояния | Redis |
| Фоновые задачи | ARQ или Celery |
| Валидация | Pydantic 2 |
| Тестирование | pytest |
| Контейнеризация | Docker |
| Управление сервисами | Docker Compose |
| Антивирус | ClamAV |
| Шифрование | AES-256-GCM или современный AEAD |

Все версии библиотек должны быть совместимыми и зафиксированными в lock-файле.

Не использовать SQLite в качестве основной производственной базы.

### 2.2. Архитектурная схема

```
Telegram User
↓
Telegram Bot API
↓
aiogram Bot
↓
Backend / Business Services
↓
Permission Service
↓
PostgreSQL + MinIO + Redis
↓
Background Workers
```

### 2.3. Назначение компонентов

**Telegram Bot** — обеспечивает весь пользовательский интерфейс и взаимодействие с системой.

**Backend** — содержит бизнес-логику, авторизацию, права доступа, операции с записями, файлами, импортом, аудитом и резервными копиями.

**PostgreSQL** — хранит структурированные данные, пользователей, роли, категории, записи, права, метаданные и историю.

**MinIO** — хранит физические файлы, фотографии, видео, документы и другие вложения.

**Redis** — используется для FSM, кеширования, очередей, блокировок и временных данных.

**Background Worker** — выполняет длительные операции: импорт, проверку файлов, OCR, создание резервных копий и обработку медиа.

### 2.4. Важное ограничение интерфейса

В проекте не должно быть:

- Web Admin Panel.
- Отдельного frontend.
- Browser Dashboard.
- Пользовательского сайта.
- Обязательного браузерного кабинета.
- Управления системой через браузер.

Все предусмотренные операции должны выполняться через Telegram.

Внутренние технические API, если они используются для связи компонентов, не являются пользовательской веб-панелью и не должны предоставлять публичный административный интерфейс.

При перемещении записи обязательно повторно проверять права доступа.

Перемещение не должно автоматически открывать закрытую информацию новым пользователям.

## 5. СИСТЕМА ГРУПП И ДОСТУПА

Реализовать комбинированную модель Mixed Access.

Пользователь может быть назначен в одну или несколько рабочих категорий.

Например:

- Сотрудник A — Холодка.
- Сотрудник B — 2й Этап.
- Сотрудник C — Клоузеры.
- Сотрудник D — Холодка и Общее.
- Сотрудник E — Клоузеры и Общее.

Система должна поддерживать любые комбинации.

### 5.1. Группы

Создать четыре стандартные группы:

- GROUP_HOLODKA.
- GROUP_SECOND_STAGE.
- GROUP_CLOSERS.
- GROUP_GENERAL.

Названия групп в интерфейсе отображать на русском.

Суперадмин может назначать пользователей в группы.

Босс может управлять рабочими разрешениями в рамках предоставленных полномочий.

### 5.2. Уровни видимости

Предусмотреть:

- ALL_EMPLOYEES — все активные сотрудники.
- BOSSES_ONLY — боссы и суперадмин.
- GROUP — конкретная группа.
- SELECTED_USERS — выбранные пользователи.
- PRIVATE — только явно назначенные пользователи и суперадмин.

### 5.3. Правила доступа

Использовать Default Deny.

Если разрешение не установлено, доступ запрещён.

Обязательные проверки:

1. Пользователь существует.
2. Пользователь активен.
3. Пользователь не заблокирован.
4. Его роль разрешает операцию.
5. Он состоит в необходимой группе либо имеет индивидуальное разрешение.
6. Категория доступна.
7. Запись доступна.
8. Вложение доступно.

Проверять права на сервере при каждом действии.

Нельзя полагаться только на скрытие кнопок.

### 5.4. Изменение принадлежности сотрудника

Суперадмин должен иметь возможность:

- Добавить сотрудника в категорию.
- Удалить сотрудника из категории.
- Назначить несколько категорий.
- Изменить группы.
- Временно заблокировать доступ.
- Полностью отозвать доступ.
- Просмотреть, какие разделы доступны сотруднику.

После изменения групп права должны применяться немедленно.

Кешированные разрешения должны инвалидироваться.

## 6. СТРУКТУРА ДАННЫХ

Внутри каждой из четырёх категорий реализовать универсальную систему хранения информации.

### 6.1. Типы информации

Обязательные типы:

1. CREDENTIALS — логины и пароли.
2. SIP — телефония.
3. LINKS — ссылки.
4. SETTINGS — настройки.
5. INSTRUCTIONS — инструкции.
6. FILES — файлы и медиа.
7. OTHER — прочая информация.

### 6.2. Универсальная запись

Каждая запись должна иметь:

- UUID.
- Название.
- Описание.
- Основную категорию сотрудников.
- Тип информации.
- Подкатегорию.
- Пользовательские поля.
- Теги.
- Вложения.
- Уровень доступа.
- Группы доступа.
- Индивидуальные разрешения.
- Автора.
- Последнего редактора.
- Дату создания.
- Дату изменения.
- Статус.
- Историю изменений.

### 6.3. Динамические поля

Поддерживать:

- TEXT.
- LONG_TEXT.
- PASSWORD.
- SECRET.
- URL.
- EMAIL.
- PHONE.
- NUMBER.
- BOOLEAN.
- DATE.
- DATETIME.
- JSON.
- FILE_REFERENCE.
- MULTISELECT.

Боссы должны иметь возможность создавать пользовательские поля при добавлении или редактировании записей.

### 6.4. CREDENTIALS

Структура:

- Название сервиса.
- URL.
- Login.
- Password.
- Email.
- Дополнительные данные.
- Примечание.
- Срок действия.
- Ответственный.
- Вложения.

Пароли хранить только в зашифрованном виде.

### 6.5. SIP

Структура:

- Название.
- SIP Username.
- SIP Password.
- SIP Domain.
- SIP Server.
- Port.
- Transport.
- Extension.
- Phone Number.
- Outbound Proxy.
- Registrar.
- Authentication Username.
- Codec.
- Дополнительные настройки.
- Инструкция.
- Вложения.

Предусмотреть копирование отдельных полей.

### 6.6. LINKS

Структура:

- Название.
- URL.
- Описание.
- Назначение.
- Категория.
- Ответственный.
- Дополнительные параметры.

Проверять корректность URL и разрешать только безопасные схемы, прежде всего HTTP и HTTPS.

### 6.7. SETTINGS

Хранить:

- Название настройки.
- Приложение или оборудование.
- Параметр.
- Значение.
- Описание.
- Инструкцию.
- Файлы конфигурации.

Секретные значения шифровать.

### 6.8. INSTRUCTIONS

Хранить:

- Название.
- Краткое описание.
- Полный текст.
- Последовательность действий.
- Изображения.
- Видео.
- Документы.
- Ссылки.

## 10. ФАЙЛОВОЕ ХРАНИЛИЩЕ

Реализовать полноценное централизованное хранилище файлов.

Не использовать Telegram file_id в качестве единственного способа хранения.

### 10.1. Поддерживаемые форматы

Изображения: JPG/JPEG, PNG, WEBP, GIF, HEIC/HEIF, SVG (как загружаемый файл без небезопасного встроенного рендеринга).

Документы: PDF, DOC, DOCX, XLS, XLSX, PPT, PPTX, ODT, ODS, TXT, RTF.

Архивы: ZIP, RAR, 7Z, TAR, GZ.

Медиа: MP4, MOV, AVI, MKV, MP3, WAV, OGG.

Данные: JSON, JSONL, XML, CSV, TSV, YAML, SQL, INI, ENV.

Также разрешить произвольные форматы с безопасной обработкой.

### 10.2. Загрузка

Поддержать:

- Загрузку фотографий.
- Загрузку документов.
- Загрузку видео.
- Загрузку аудио.
- Загрузку архивов.
- Загрузку нескольких файлов.
- Добавление файлов к записи.
- Создание записи с вложениями.
- Сохранение файла в отдельную категорию.
- Замену файла.
- Версионирование.

### 10.3. Обработка загрузки

После получения файла:

1. Проверить пользователя.
2. Проверить права на загрузку.
3. Проверить лимит размера.
4. Получить файл.
5. Проверить фактический формат.
6. Проверить MIME.
7. Рассчитать SHA-256.
8. Поместить файл в карантин.
9. Выполнить антивирусную проверку.
10. Сохранить объект в MinIO.
11. Сохранить метаданные в PostgreSQL.
12. Привязать к записи или категории.
13. Зафиксировать действие в аудите.
14. Сообщить результат.

Инфицированные и неподтверждённые файлы не выдавать сотрудникам.

### 10.4. Управление файлами

Реализовать:

- Просмотр.
- Скачивание.
- Переименование.
- Перемещение.
- Копирование.
- Замена.
- Удаление.
- Восстановление.
- Версионирование.
- Просмотр метаданных.
- Поиск.
- Фильтрацию.

### 10.5. Безопасность файлов

Предусмотреть:

- MIME validation.
- Проверку magic bytes.
- Проверку расширения.
- Защиту от path traversal.
- Защиту от ZIP Bomb.
- Ограничения распаковки.
- Изоляцию обработки архивов.
- ClamAV.
- Запрет исполнения загруженного содержимого.
- Проверку разрешений перед каждым скачиванием.

Все файлы должны храниться приватно.

Не создавать постоянные публичные URL.

## 13. АРХИВ И УДАЛЕНИЕ

Реализовать отдельный архив.

Боссы могут:

- Архивировать записи.
- Архивировать категории.
- Просматривать архив.
- Восстанавливать записи.
- Удалять записи окончательно в рамках разрешённой политики.

Суперадмин может управлять архивом полностью.

Обычное удаление должно быть логическим, с возможностью восстановления в установленный срок.

Окончательное удаление должно требовать подтверждения.

При удалении категории система должна предложить:

- Переместить записи.
- Архивировать категорию вместе с содержимым.
- Отменить операцию.

Удаление записи не должно автоматически удалять общие файлы, используемые другими записями.

## 17. ШИФРОВАНИЕ И ЗАЩИТА СЕКРЕТОВ

Рабочие пароли, SIP-пароли, токены и другие секреты должны храниться в зашифрованном виде.

Использовать AES-256-GCM или другой современный AEAD.

Предусмотреть:

- Мастер-ключ.
- Отдельное хранение ключей.
- Версионирование ключей.
- Ротацию ключей.
- Шифрование чувствительных полей.
- Маскирование секретов.
- Отдельное действие для раскрытия.
- Отдельное действие для копирования.
- Аудит раскрытия.
- Аудит копирования.
- Защиту временных данных.
- Запрет логирования секретов.

Не хранить мастер-ключ рядом с зашифрованными данными.

Обычные Telegram-сообщения не являются сквозным зашифрованным хранилищем.

Поэтому особо чувствительные секреты не должны бесконтрольно отправляться в обычную историю чата.

Предусмотреть безопасную выдачу с дополнительным подтверждением, минимальным временем показа и очисткой сообщений там, где Telegram это позволяет.

Не обещать гарантированное удаление ранее доставленных сообщений со всех устройств пользователя.
